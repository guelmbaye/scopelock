What it does

You paste a planning contract and one proposed diff. Claude proposes a verdict (Aligned, Conflict or Unplanned) with one piece of evidence: a quote and the heading path it claims the quote sits under. Deterministic code then checks that the quote is one complete planning line under exactly that path. If the check fails, the verdict becomes Unplanned. The model interprets; the verifier decides what counts as evidence.

One action: pressing Check Alignment

Reference route (3 stops)

A reference route through the finished code; it wasn't toured interactively.

  1. public/state.js → reduce, case "check". Empty panes return request: null and the Not checked state, so nothing is sent. Otherwise the state becomes checking, which locks the inputs, and the exact snapshot to send is returned. app.js → dispatch / send does the actual fetch.
  2. src/check.js → runCheck. Calls model.propose. Any throw becomes check_failed. A structurally impossible proposal (Aligned or Conflict without evidence, or Unplanned with evidence) is rejected, never repaired. Valid evidence goes to the verifier, and only a verifier rejection turns the verdict into unplanned with an evidenceCheck.
  3. src/verify.js → verifyEvidence. Normalizes whitespace only. The quote must equal one entire block from parsePlan, and that block's heading path must equal the claimed path exactly. The result is quote_not_found, wrong_path (with the paths where the quote was actually found), or ok.

A practice to reuse

Test the contract where it crosses a library boundary, not just your own code.

The spec required the output schema itself to tie evidence to the verdict: Aligned or Conflict must carry evidence, and Unplanned must carry null. A test that asserts that observable property on what is actually sent (test/check.test.js → "schema reaches the API with both branches enforced") showed that the SDK's default schema transform turned enum/const into description text. Nothing failed at runtime, and the defensive check in readProposal would have hidden the gap. The fix was one documented option (transform: false), recorded under Revisions in devpost/checklist.md, with no product change.

On another project: when the plan states a guarantee that a dependency is supposed to provide, write one check against the dependency's real output. A compatibility probe right after install (as in slice 1) and an assertion of the guaranteed property catch drift that "it works" demos don't.
