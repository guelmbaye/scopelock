SCOPELOCK

Checks whether a proposed code change still belongs to the product you decided to build, and shows the planning evidence behind the verdict.

Kernel: a change can be valid code and still be the wrong change. SCOPELOCK judges a diff against the plan, not against the model's sense of good engineering. The model can interpret, but it cannot invent the source: every piece of evidence must be found word for word in the planning text, under the section the model claims. The same line means different things under "Later" and "Now", so the evidence is the quote plus its verified location.

Who it's for

A developer working with AI coding agents who has already done the planning. Today, drift slips through: the agent adds a feature that was explicitly pushed to "later". It compiles, tests pass, the UI looks good, and catching it depends on remembering the decision.

The core loop

Aligned

Clearly supported by a planning decision.

Unplanned

No supporting or conflicting decision, or the citation couldn't be verified (quote missing, or not under the claimed section).

Conflict

Contradicts something explicitly deferred or excluded.

What "working" looks like: the flip test

Same diff, same quoted line. The verdict changes only because the line's verified section changed.

Boundary

Now: the POC
  • One planning contract: editable planning text in the page.
  • One coherent proposed change: a pasted diff representing a single product change.
  • One verdict + a short explanation + an evidence trail.
  • Citation check on quote and location: verbatim quote inside the claimed section/heading; if either fails, fall back to Unplanned / review plan.
  • A sample plan and sample diff(s) ready to load for the flip test.
Later
  • Mixed diffs: splitting into separate changes, a verdict per change, rules for combining them.
  • GitHub PR integration, CI check, IDE extension, agent hook.
  • Reading docs and diffs straight from the repo (CLI or file loading).
Explicitly cut
  • Mixed / multi-change diffs: a stated POC limitation; a weak version would undermine the proof.
  • General code review, bug or security detection: these judge technical quality, not product fit.
  • Project-management features, chat over the repo: a different product.

Planning-review companion to scope.md, which is the source of truth. Not part of the SCOPELOCK product.
